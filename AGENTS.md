# AGENTS.md

## 1. Назначение проекта

Проект предназначен для ведения профессионального резюме и портфолио в Markdown и последующей автоматизированной сборки итоговых документов в формате DOCX.

Markdown-файлы содержат текстовое содержание. Графические материалы хранятся отдельно в `assets/`. Исходные материалы и файлы сборки не являются частью публикуемого Git-репозитория.

## 2. Структура рабочей директории

```text
Resume/
├── AGENTS.md
├── .gitignore
├── README.md
│
├── resume/
│   ├── summary.md
│   ├── experience.md
│   ├── competencies.md
│   ├── tools.md
│   └── education.md
│
├── portfolio/
│   └── <project>/
│       ├── project.md
│       └── assets/
│
├── sources/
│   ├── AGENTS.md
│   └── ...
│
└── export/
    ├── templates/
    ├── work/
    └── final/
```

Для групп проектов допускаются дополнительные уровни внутри `portfolio/`, например:

```text
portfolio/
└── developments/
    └── <project>/
        ├── project.md
        └── assets/
```

## 3. Границы Git-репозитория

В Git публикуются только презентационные файлы:

- `README.md`;
- `resume/`;
- `portfolio/`;
- технически необходимый `.gitignore`.

Локальными и исключёнными из Git должны оставаться:

- корневой `AGENTS.md`;
- `sources/`;
- `export/`.

Не добавлять в Git исходные PDF, архивы, модели, временные файлы, шаблоны сборки, промежуточные результаты и итоговые DOCX вне структуры `portfolio/**/assets/`.

Файлы в `portfolio/**/assets/` являются частью портфолио и могут храниться в Git.

## 4. Источники истины

### Текстовое содержание

Источником истины для текста являются:

- `resume/*.md`;
- `portfolio/**/project.md`.

Содержательные исправления сначала вносятся в Markdown. Итоговый DOCX не используется как первичный источник текста.

### Графические материалы

Источником истины для итоговой графики являются файлы в:

```text
portfolio/**/assets/
```

В `assets/` хранятся только отобранные и подготовленные изображения, предназначенные для использования при сборке портфолио.

### Исходные материалы

Оригиналы и рабочие источники хранятся в:

```text
sources/
```

К ним относятся PDF, модели, архивы, таблицы, исходные изображения, внешние материалы и другие файлы, из которых готовятся данные для резюме и портфолио.

### Инструкции агента

Корневой `AGENTS.md` и `sources/AGENTS.md` должны содержательно совпадать.

Корневой файл используется агентом как рабочая инструкция. Копия в `sources/` хранится вместе с исходными материалами.

## 5. README

`README.md` содержит только:

- контактные данные;
- навигацию по резюме и портфолио;
- краткие пояснения к разделам непосредственно в навигации.

Не добавлять в `README.md` служебные инструкции, описание процесса сборки, рабочие заметки, правила для агента и внутреннюю структуру проекта.

## 6. Resume

Каталог `resume/` содержит профессиональный профиль:

- аннотацию;
- опыт работы и достижения;
- общие компетенции;
- инструменты;
- образование и языки.

Подробное описание объектов и разработок в `resume/` не переносится.

Принятые правила формулировок:

- не указывать численность людей под руководством, если это отдельно не согласовано;
- использовать формулировки уровня `расчётная группа`, `инженеры`, `отделы ген- и субподрядной организаций`;
- BIM и автоматизацию объединять в направление `Информационное моделирование`;
- для собственных средств автоматизации использовать формулировку `специализированные утилиты собственной разработки` либо конкретное название продукта;
- MagiCAD Create описывать как универсальную расчётную базу вентиляционного оборудования с привязкой расчётных параметров к параметризованным и специфицируемым Revit-семействам;
- не представлять незавершённый Revit-плагин и BIM-стандарт как реализованные достижения;
- не придумывать обязанности, достижения, метрики и уровни ответственности, не подтверждённые источниками или пользователем.

## 7. Portfolio

Каталог `portfolio/` содержит только проекты:

- инженерные объекты;
- BIM-проекты;
- IT-разработки;
- другие завершённые или демонстрируемые работы.

Единица проекта:

```text
portfolio/<project>/
├── project.md
└── assets/
```

`project.md` содержит текстовое описание проекта. В зависимости от проекта могут использоваться:

- название;
- локация;
- стадия;
- роль;
- выполненные работы;
- технические параметры;
- результат или особенности решения, если они не дублируют выполненные работы.

В `project.md` не размещать изображения, ссылки на локальные изображения, галереи, placeholders и служебные указания по будущей вёрстке.

Для завершённых работ использовать завершённые формы: `выполнил`, `разработал`, `создал`, `согласовал` либо нейтральные формы `выполнено`, `разработано`.

Не смешивать роль и выполненные работы.

Избегать хронологических связок `ранее`, `потом`, `сейчас`, если хронология сама по себе не является значимой.

## 8. Графические материалы

Графика не встраивается в Markdown.

Итоговые изображения для конкретного проекта хранятся в его `assets/` и используются только на этапе сборки DOCX.

Рабочий процесс:

```text
sources/
    ↓
извлечение / рендер / обрезка / подготовка
    ↓
portfolio/<project>/assets/
    ↓
сборка DOCX
```

Правила:

- оригиналы в `sources/` не изменять;
- извлекать изображения, рендерить страницы, обрезать и преобразовывать только в новые файлы;
- итоговый подготовленный материал помещать в соответствующий `portfolio/**/assets/`;
- не переносить в `assets/` промежуточные, дублирующие и заведомо неиспользуемые файлы;
- не выбирать самостоятельно ракурсы из инженерных моделей, если пользователь должен подготовить их вручную;
- не изменять техническое содержание изображения ради декоративного эффекта;
- не добавлять графику в Markdown даже после окончательного выбора изображений.

## 9. Sources

`sources/` — локальное хранилище исходных и рабочих материалов.

Запрещено без отдельной задачи:

- изменять оригинальные исходники;
- удалять их;
- переименовывать;
- переносить в Git;
- заменять исходные файлы обработанными версиями.

Разрешено:

- читать и анализировать;
- извлекать графику;
- рендерить страницы;
- копировать;
- преобразовывать копии;
- использовать как основу для подготовки файлов в `portfolio/**/assets/`.

Материалы, найденные во внешних источниках, сначала сохранять в `sources/`. В `assets/` переносить только выбранную итоговую версию.

## 10. Export и шаблоны

`export/` используется только локально и исключён из Git.

Рабочая структура:

```text
export/
├── templates/
├── work/
└── final/
```

### templates

На этапе выбора допускается несколько вариантов шаблонов резюме и портфолио.

После выбора:

- сохранить только принятый шаблон или принятый комплект шаблонов;
- остальные варианты удалить;
- не хранить отвергнутые варианты в репозитории или финальной рабочей структуре.

### work

Используется для промежуточных результатов сборки, тестовых документов, рендеров и технических файлов.

Содержимое `work/` не является источником истины.

### final

Содержит итоговые DOCX, предназначенные для передачи пользователю.

## 11. Сборка

Итоговая автоматизированная сборка выполняется только в формате DOCX.

PDF не генерировать, если пользователь отдельно этого не запросил. Пользователь самостоятельно получает PDF из финального Word-документа.

Сборка должна использовать:

- текст из Markdown;
- итоговую графику из `portfolio/**/assets/`;
- выбранный шаблон из `export/templates/`.

DOCX является производным артефактом.

Содержательные исправления не вносить только в DOCX. При изменении текста сначала обновить соответствующий Markdown и затем пересобрать документ.

Настройки представления могут определяться шаблоном:

- шрифты;
- размеры;
- сетка;
- интервалы;
- колонтитулы;
- размещение изображений;
- подписи;
- разрывы страниц;
- другие параметры вёрстки.

## 12. Выполнение задач

Перед выполнением любой нетривиальной задачи сначала:

1. определить цель;
2. определить входные данные;
3. определить ожидаемые изменения;
4. определить затрагиваемые файлы;
5. обозначить границы задачи;
6. представить план пользователю;
7. дождаться явного подтверждения плана.

Не начинать выполнение до согласования, если пользователь прямо не дал команду выполнить уже согласованный план.

Issue является основной единицей изменения.

Один issue должен иметь ограниченный и проверяемый результат. Не смешивать без явной необходимости:

- подготовку исходных данных;
- редактирование текста;
- обработку изображений;
- разработку шаблонов;
- финальную сборку.

Если issue посвящён изображениям — не менять текстовые Markdown-файлы.

Если issue посвящён тексту — не менять графику и шаблоны.

Если issue посвящён шаблону — не менять фактическое содержание резюме и портфолио.

Если issue посвящён сборке — не менять источники и не пересматривать содержание без отдельного согласования.

Не переходить к следующему этапу workflow автоматически после завершения текущего.

## 13. Ограничения и запреты

Запрещено:

- придумывать факты, достижения, обязанности и метрики;
- менять смысл пользовательских формулировок без необходимости;
- добавлять графику непосредственно в Markdown;
- коммитить `AGENTS.md`, `sources/` или `export/`;
- изменять оригинальные файлы в `sources/`;
- самостоятельно выбирать инженерные ракурсы, если это не поручено явно;
- самостоятельно менять структуру проекта без согласования;
- выполнять следующий этап workflow до принятия текущего;
- создавать PDF в рамках стандартного процесса сборки;
- редактировать итоговый DOCX как единственный источник содержательных изменений.
