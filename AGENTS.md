# AGENTS.md

## 1. Назначение проекта

Проект предназначен для ведения профессионального резюме и портфолио в Markdown, хранения отобранной графики и шаблонов оформления, а также последующей автоматизированной сборки итоговых документов в формате DOCX.

Разделение ответственности:

- Markdown — текстовое содержание;
- `portfolio/**/assets/` — итоговая графика портфолио;
- `export/templates/` — сохраняемые шаблоны и правила компоновки;
- `export/final/` — итоговые DOCX после финальной сборки;
- `sources/` — локальные исходные материалы;
- `.codex/` — локальная временная рабочая зона агента.

PDF в стандартном процессе не формируется.

## 2. Структура рабочей директории

```text
Resume/
├── AGENTS.md
├── .gitignore
├── README.md
│
├── resume/
│   ├── summary.md
│   ├── experience.md
│   ├── competencies.md
│   ├── tools.md
│   └── education.md
│
├── portfolio/
│   └── <project>/
│       ├── project.md
│       └── assets/
│
├── export/
│   ├── templates/
│   │   └── <template>/
│   │       ├── resume-template.docx
│   │       ├── portfolio-template.docx
│   │       └── layout.yaml
│   └── final/
│       └── ...
│
├── sources/
│   ├── AGENTS.md
│   └── ...
│
└── .codex/
    ├── work/
    ├── build/
    ├── previews/
    └── ...
```

Для групп проектов допускаются дополнительные уровни внутри `portfolio/`, например:

```text
portfolio/
└── developments/
    └── <project>/
        ├── project.md
        └── assets/
```

Подкаталоги внутри `.codex/` могут создаваться по необходимости. Их имена не являются частью публичной структуры проекта.

## 3. Границы Git-репозитория

В Git допускается хранить:

- `AGENTS.md`;
- `.gitignore`;
- `README.md`;
- `resume/`;
- `portfolio/`, включая `portfolio/**/assets/`;
- `export/templates/`;
- `export/final/`, когда финальные DOCX должны быть сохранены в репозитории.

Локальными и исключёнными из Git должны оставаться:

- `sources/`;
- `.codex/`.

Не добавлять в Git:

- исходные PDF, архивы, модели и таблицы из `sources/`;
- промежуточные рендеры;
- contact sheets;
- временные DOCX;
- тестовые сборки;
- вспомогательные build-скрипты и одноразовые утилиты из `.codex/`;
- кэши, runtime-файлы и другие воспроизводимые рабочие артефакты.

Исключение: изображения в `portfolio/**/assets/` являются отобранной итоговой графикой и входят в репозиторий.

## 4. Источники истины

### Текстовое содержание

Источником истины для текста являются:

- `resume/*.md`;
- `portfolio/**/project.md`.

Содержательные исправления сначала вносятся в Markdown.

Итоговый DOCX и шаблонный DOCX не являются первичными источниками текста.

### Графические материалы

Источником истины для итоговой графики являются:

```text
portfolio/**/assets/
```

В `assets/` хранятся только выбранные и подготовленные изображения, предназначенные для реального использования в портфолио.

### Шаблоны и компоновка

Источником истины для дизайна и правил сборки являются:

```text
export/templates/
```

Каждый сохраняемый шаблон может включать:

- `resume-template.docx`;
- `portfolio-template.docx`;
- `layout.yaml`.

`layout.yaml` описывает правила компоновки, связь блоков текста с графикой, размеры и роли изображений, поведение разрывов и другие параметры сборки. Он не должен дублировать фактическое содержание Markdown.

### Исходные материалы

Оригиналы и рабочие источники хранятся в:

```text
sources/
```

К ним относятся PDF, модели, архивы, таблицы, исходные изображения, внешние материалы и другие файлы, из которых готовятся данные для резюме и портфолио.

### Рабочие артефакты

`.codex/` не является источником истины.

В нём разрешено хранить:

- временные build-скрипты;
- промежуточные изображения;
- тестовые DOCX;
- preview-рендеры;
- служебные выгрузки;
- кэши;
- другие воспроизводимые рабочие файлы.

Содержимое `.codex/` должно быть безопасно удалить и пересоздать.

### Инструкции агента

Корневой `AGENTS.md` является канонической версией инструкций.

`sources/AGENTS.md` — локальная зеркальная копия, хранящаяся вместе с исходниками. При изменении корневого `AGENTS.md` копию в `sources/` следует синхронизировать, когда локальный каталог доступен.

## 5. README

`README.md` содержит только:

- контактные данные;
- навигацию по резюме и портфолио;
- краткие пояснения к разделам непосредственно в навигации.

Не добавлять в `README.md`:

- служебные инструкции;
- описание процесса сборки;
- рабочие заметки;
- правила для агента;
- внутреннюю структуру проекта.

## 6. Resume

Каталог `resume/` содержит профессиональный профиль:

- аннотацию;
- опыт работы и достижения;
- общие компетенции;
- инструменты;
- образование и языки.

Подробное описание объектов и разработок в `resume/` не переносится.

Принятые правила формулировок:

- не указывать численность людей под руководством, если это отдельно не согласовано;
- использовать формулировки уровня `расчётная группа`, `инженеры`, `отделы ген- и субподрядной организаций`;
- BIM и автоматизацию объединять в направление `Информационное моделирование`;
- для собственных средств автоматизации использовать формулировку `специализированные утилиты собственной разработки` либо конкретное название продукта;
- MagiCAD Create описывать как универсальную расчётную базу вентиляционного оборудования с привязкой расчётных параметров к параметризованным и специфицируемым Revit-семействам;
- не представлять незавершённый Revit-плагин и BIM-стандарт как реализованные достижения;
- не придумывать обязанности, достижения, метрики и уровни ответственности, не подтверждённые источниками или пользователем.

## 7. Portfolio

Каталог `portfolio/` содержит только проекты:

- инженерные объекты;
- BIM-проекты;
- IT-разработки;
- другие завершённые или демонстрируемые работы.

Единица проекта:

```text
portfolio/<project>/
├── project.md
└── assets/
```

`project.md` содержит текстовое описание проекта. В зависимости от проекта могут использоваться:

- название;
- локация;
- стадия;
- роль;
- выполненные работы;
- технические параметры;
- результат или особенности решения, если они не дублируют выполненные работы.

В `project.md` не размещать:

- изображения;
- ссылки на локальные изображения;
- галереи;
- placeholders;
- служебные указания по будущей вёрстке.

Для завершённых работ использовать завершённые формы: `выполнил`, `разработал`, `создал`, `согласовал` либо нейтральные формы `выполнено`, `разработано`.

Не смешивать роль и выполненные работы.

Избегать хронологических связок `ранее`, `потом`, `сейчас`, если хронология сама по себе не является значимой.

## 8. Графические материалы

Графика не встраивается в Markdown.

Итоговые изображения для конкретного проекта хранятся в его `assets/` и используются на этапе сборки DOCX.

Рабочий процесс:

```text
sources/
    ↓
.codex/ — анализ, рендер, обрезка, промежуточная подготовка
    ↓
portfolio/<project>/assets/ — утверждённый итоговый asset
    ↓
export/templates/ — правила компоновки
    ↓
export/final/ — итоговый DOCX
```

Правила:

- оригиналы в `sources/` не изменять;
- извлекать изображения, рендерить страницы, обрезать и преобразовывать только в новые файлы;
- промежуточные варианты держать в `.codex/`;
- в `portfolio/**/assets/` переносить только итоговый выбранный материал;
- не хранить в `assets/` дублирующие и заведомо неиспользуемые файлы;
- технические листы из PDF рассматривать как источник графики, а не как готовую иллюстрацию по умолчанию;
- для портфолио предпочтительно использовать содержательные фрагменты планов, схем, аксонометрий и моделей, а не целые листы с большими пустыми полями;
- не выбирать самостоятельно ракурсы из инженерных моделей, если пользователь должен подготовить их вручную;
- не изменять техническое содержание изображения ради декоративного эффекта;
- не добавлять графику в Markdown даже после окончательного выбора изображений.

## 9. Sources

`sources/` — локальное хранилище исходных и рабочих материалов.

Запрещено без отдельной задачи:

- изменять оригинальные исходники;
- удалять их;
- переименовывать;
- переносить их в Git;
- заменять исходные файлы обработанными версиями.

Разрешено:

- читать и анализировать;
- извлекать графику;
- рендерить страницы;
- копировать;
- преобразовывать копии;
- использовать как основу для подготовки файлов в `portfolio/**/assets/`.

Материалы, найденные во внешних источниках, сначала сохранять в `sources/`, если они нужны как исходник. В `assets/` переносить только выбранную итоговую версию.

## 10. .codex

`.codex/` — локальный рабочий контур Codex и других агентов.

Использовать его для:

- `.codex/work/` — промежуточные результаты;
- `.codex/build/` — сборочные скрипты и временная логика;
- `.codex/previews/` — рендеры страниц и визуальные проверки;
- иных временных подкаталогов по необходимости.

Правила:

- `.codex/` всегда остаётся вне Git;
- ссылки из сохраняемых `layout.yaml` не должны зависеть от временных файлов в `.codex/`, если без них невозможно воспроизвести итоговый шаблон;
- если build-логика необходима для постоянного воспроизводимого процесса, перед финализацией отдельно определить, должна ли она остаться временной в `.codex/` или быть перенесена в сохраняемую структуру;
- не использовать `.codex/` как место хранения единственной копии значимого текста, графики или шаблона.

## 11. Export и шаблоны

`export/` содержит сохраняемые результаты процесса оформления и сборки и входит в Git.

Рабочая структура:

```text
export/
├── templates/
│   └── <template>/
│       ├── resume-template.docx
│       ├── portfolio-template.docx
│       └── layout.yaml
└── final/
    └── ...
```

### templates

На этапе выбора допускается несколько вариантов шаблонов резюме и портфолио.

Каждая концепция должна хранить только сохраняемые файлы, необходимые для её оценки и последующего воспроизведения.

Тестовые сборки, page-preview PNG и иные временные результаты хранить в `.codex/`, а не в `export/templates/`.

После выбора:

- сохранить только принятый шаблон или принятый комплект шаблонов;
- остальные концепции удалить;
- привести выбранный `layout.yaml` в соответствие фактической финальной логике сборки.

### final

`export/final/` предназначен для итоговых DOCX.

Финальные файлы создаются только после отдельного этапа сборки и пользовательского утверждения шаблона.

## 12. Сборка

Итоговая автоматизированная сборка выполняется только в формате DOCX.

PDF не генерировать, если пользователь отдельно этого не запросил. Пользователь самостоятельно получает PDF из финального Word-документа.

Сборка должна использовать:

- текст из Markdown;
- итоговую графику из `portfolio/**/assets/`;
- выбранный шаблон из `export/templates/`.

Итоговый DOCX сохраняется в `export/final/`.

DOCX является производным артефактом.

Содержательные исправления не вносить только в DOCX. При изменении текста сначала обновить соответствующий Markdown и затем пересобрать документ.

Настройки представления могут определяться шаблоном:

- шрифты;
- размеры;
- сетка;
- интервалы;
- колонтитулы;
- размещение изображений;
- подписи;
- разрывы страниц;
- другие параметры вёрстки.

Изображения должны быть частью композиции соответствующего текстового материала. Не создавать отдельные страницы только ради демонстрации изображения, если пользователь отдельно этого не запросил.

## 13. Выполнение задач

Перед выполнением любой нетривиальной задачи сначала:

1. определить цель;
2. определить входные данные;
3. определить ожидаемые изменения;
4. определить затрагиваемые файлы;
5. обозначить границы задачи;
6. представить план пользователю;
7. дождаться явного подтверждения плана.

Не начинать выполнение до согласования, если пользователь прямо не дал команду выполнить уже согласованный план.

Issue является основной единицей изменения.

Один issue должен иметь ограниченный и проверяемый результат. Не смешивать без явной необходимости:

- подготовку исходных данных;
- редактирование текста;
- обработку изображений;
- разработку шаблонов;
- финальную сборку.

Если issue посвящён изображениям — не менять текстовые Markdown-файлы.

Если issue посвящён тексту — не менять графику и шаблоны.

Если issue посвящён шаблону — не менять фактическое содержание резюме и портфолио.

Если issue посвящён сборке — не менять источники и не пересматривать содержание без отдельного согласования.

Не переходить к следующему этапу workflow автоматически после завершения текущего.

## 14. Ограничения и запреты

Запрещено:

- придумывать факты, достижения, обязанности и метрики;
- менять смысл пользовательских формулировок без необходимости;
- добавлять графику непосредственно в Markdown;
- коммитить `sources/` или `.codex/`;
- изменять оригинальные файлы в `sources/`;
- самостоятельно выбирать инженерные ракурсы, если это не поручено явно;
- самостоятельно менять структуру проекта без согласования;
- выполнять следующий этап workflow до принятия текущего;
- создавать PDF в рамках стандартного процесса сборки;
- редактировать итоговый DOCX как единственный источник содержательных изменений.
